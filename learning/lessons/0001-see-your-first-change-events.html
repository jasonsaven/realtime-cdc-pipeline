Lesson 1 · Stage 1: Postgres as a CDC source

See your first change events

You'll make Postgres show you every insert, update and delete as a stream of events. This is the raw material the rest of the pipeline is built on. About 30 minutes.

Why this matters for your mission: Debezium, Kafka, Flink and StarRocks only ever see what Postgres hands them here. If you can read this stream directly, you can troubleshoot the very first hop of the pipeline.

Three ideas, just enough to start

1. The WAL: Postgres writes it down first

Before Postgres changes any table on disk, it appends a record of the change to the write-ahead log (WAL). The docs put it plainly: changes to data files "must be written only after those changes have been logged."[1] The WAL exists for crash recovery, but it has a useful side effect: Postgres already keeps an ordered list of every change ever made.

Every position in that log has an address called an LSN (Log Sequence Number), written like 0/1BDDA38. LSNs only go up, so they work like page numbers in the log.

2. Logical decoding: turning the log into row changes

The WAL describes changes at the storage level ("these bytes on this page changed"), which is useless to anyone outside Postgres. Logical decoding translates it into readable row changes, "a coherent, easy to understand format."[2] The translator is an output plugin. Today you'll use test_decoding, which prints plain text. Debezium will later use a different plugin, pgoutput, which reads the same log but produces a binary format.

This only works if Postgres runs with wal_level=logical, which makes it record a bit more detail in the WAL. The project's docker-compose.yml already sets this; open the file and find the line.

3. Replication slots: the bookmark

A replication slot is a named bookmark that Postgres keeps for one consumer. It remembers how far that consumer has read.[2] Reading changes comes in two styles:[3]

  • pg_logical_slot_peek_changes shows you the changes but doesn't move the bookmark.
  • pg_logical_slot_get_changes shows you the changes and moves the bookmark past them, so you won't see them again.
  INSERT / UPDATE / DELETE
            │
            ▼
   WAL  ─────────────────────────────────▶  (ordered by LSN)
            │  logical decoding (output plugin)
            ▼
   replication slot  "how far has this consumer read?"
            │
            ▼
   you, today (later: Debezium)

Do it

  1. Make the docker command available. On this Mac, Docker's command-line tool isn't on your PATH yet. In a terminal: 
    export PATH="$HOME/.docker/bin:$PATH"
docker version
    To make this permanent, add the export line to ~/.zshrc.
  2. Start Postgres from the repo root, then open a SQL prompt inside the container: 
    cd ~/code/realtime-cdc-pipeline
docker compose up -d postgres
docker compose exec postgres psql -U postgres -d shop
    Check the setting from idea 2: 
    SHOW wal_level;
  3. Create a table and a slot. 
    CREATE TABLE orders (id serial PRIMARY KEY, item text NOT NULL, qty int NOT NULL);

SELECT * FROM pg_create_logical_replication_slot('lesson1_slot', 'test_decoding');
    The slot starts reading from the LSN it returns. Anything that happened earlier, including the CREATE TABLE, comes before the bookmark.
  4. Make three changes, each in its own transaction: 
    INSERT INTO orders (item, qty) VALUES ('coffee beans', 2);
UPDATE orders SET qty = 3 WHERE id = 1;
DELETE FROM orders WHERE id = 1;
    The table is now empty. The history of what happened to it isn't.
  5. Before you run the next query, write down your guesses. How many rows will it return? (Hint: each transaction has a start and an end.) What will the DELETE line contain?
    SELECT * FROM pg_logical_slot_peek_changes('lesson1_slot', NULL, NULL);
    Check your prediction

    9 rows: a BEGIN, one change and a COMMIT for each of the 3 transactions. Each row has an lsn, a transaction id (xid) and the decoded data. Your LSNs will differ from anyone else's.

    Look closely at the DELETE line: it shows only id[integer]:1. By default Postgres records just the primary key of a deleted row. That will matter a lot downstream, and lesson 4 covers it.

  6. Test the bookmark. Run each line and compare the counts: 
    SELECT count(*) FROM pg_logical_slot_peek_changes('lesson1_slot', NULL, NULL);  -- again
SELECT count(*) FROM pg_logical_slot_get_changes('lesson1_slot', NULL, NULL);   -- consume
SELECT count(*) FROM pg_logical_slot_get_changes('lesson1_slot', NULL, NULL);   -- and again?
    What you should see

    9, 9, then 0. Peeking left the bookmark where it was. The first get read the changes and moved the bookmark, so the second get has nothing new. This is how a real consumer works: read, then record your progress.

  7. Look at the bookmark itself, then delete it: 
    SELECT slot_name, plugin, active, restart_lsn, confirmed_flush_lsn FROM pg_replication_slots;

SELECT pg_drop_replication_slot('lesson1_slot');
    confirmed_flush_lsn is how far the consumer has confirmed reading. Why drop the slot? Postgres keeps every WAL record a slot still needs, even if no one is connected. The docs warn that a forgotten slot keeps consuming storage and, in extreme cases, can force the database to shut down.[2] Lesson 2 lets you watch that happen safely.
  8. Type \q to leave psql. You can leave the container running.

Check yourself

Answer from memory, without scrolling up. Having to dig for an answer is what makes it stick.

1. You ran peek twice and got the same nine rows both times. Why?

2. Why did the DELETE event show only the id?

3. You create a slot and forget it for a month while the app keeps writing. What happens?

4. What is the WAL?
